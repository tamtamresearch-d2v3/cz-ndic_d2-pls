== Concepts

The format describes sets of predefined locations – road network sections referenced by messages of other formats. A referencing message carries only the identifier and version of the location; the full
location description is in this publication.

A set contains locations of one kind, for example:

* FCD sections – sections between ALERT-C locations, each direction of travel as a separate location,
* road weather station sections – road sections at road weather stations, valid in both directions of travel.

The format is based on the
`loc:PredefinedLocationsPublication` publication <<EN16157-2>>.

[[obalka]]
=== Envelope and publication header

A message is a DATEX II 3 document with the root element `d2:payload` of type
`loc:PredefinedLocationsPublication`. The format is identified by the root attributes `@profileName`
(`cz-ndic_d2-pls`) and `@profileVersion` (`2.0`).

The header contains:

* `feedType` – identifier of the data source (distribution) in the register of the national access point <<nap>>; the format of the message is identified
  by the `@profileName` and `@profileVersion` attributes, not by `feedType`; the `feedDescription` element is not used,
* `publicationTime` – time the publication was generated; it changes with every generated publication, even if the content has not changed,
* `publicationCreator` – `cz` and `NDIC`,
* `headerInformation` – always:
** `confidentiality` = `noRestriction`,
** `informationStatus` = `real`.

[[predef]]
=== Predefined locations

Each location of a set is a `predefinedLocationReference` element. Its type determines how the location
runs:

[cols="2,3",options="header"]
|===
|Type |Location
|`loc:PredefinedLocation` |contiguous section of one road (<<jedna-komunikace>>)
|`loc:PredefinedItinerary` |itinerary – contiguous location over several roads (<<trasy>>)
|`loc:PredefinedLocationGroup` |non-contiguous location group, e.g. an area (<<skupiny>>)
|===

*Single road rule.* The location description (`location`) is always the linear location
`loc:SingleRoadLinearLocation` – a contiguous section of one road or street whose location referencing
methods (<<polohy>>) all have the same extent. This applies to a stand-alone location and to each part of an
itinerary or group:

* A section of another road inside a junction, a short connecting link or two concurrent roads do not start
  a new part.
* If the location has an ALERT-C description, it corresponds to one path of the ALERT-C location table.

*Common properties.*

* The *identifier* (`@id`) is stable. FCD sections have it composed of ALERT-C locations:
  `TS02125T15781` is the section from location 2125 to location 15781 (location codes padded with zeros to
  five digits), the opposite direction is `TS15781T02125`.
* The *name* (`predefinedLocationName`) is given only if the location has one in the source: road weather
  station sections carry the station name (`I/43 Černá Hora`, `D0 15.742`); FCD sections, itineraries and
  groups have no name.
* The *version* (`@version`) corresponds to the Global Network release the set is derived from, in the form
  `YYMM01` (network 25.06 → `250601`):
** with each network release *all* locations of the set get a new version, including those where only the
   network version label (`linearElementReferenceModelVersion`) changed; the identifier stays,
** a new location gets a new identifier,
** messages always reference the version of the current set.
* The publication always contains all valid locations, including those published earlier. No time is given
  inside the locations.

*Parts of itineraries and groups.*

. Itineraries and groups have their own identifier and version; no name is given.
. Each part is a nested `predefinedLocation` element – a complete predefined location with its own
  identifier, version, location description and, where available, a name (the same as a stand-alone
  location).
. An itinerary or a group has at least two parts.
. Part identifiers are unique in the whole publication; the same part does not repeat within an itinerary,
  a group or the publication.
. If a part changes, both the part and the whole itinerary or group get a new version; adding or removing a
  part changes the version of the itinerary or group.

[[trasy]]
==== Itinerary over several roads

A contiguous location that runs from one road onto another (e.g. a permanent diversion route on a class II
road and a connecting class III road) is an itinerary – a `predefinedLocationReference` element of type
`loc:PredefinedItinerary`. It is a contiguous location group: each of its parts lies on one road.

.Itinerary over two roads
image::trasa-en.svg[Itinerary over several roads,width=640,align="center"]

* The parts are in the order of travel (for a bidirectional location in the order of the first direction);
  the end of a part is the start of the next one and the parts do not overlap.
* The directionality is the same in all parts; each part has its own location path `gmlLineString`.

The structure corresponds to an itinerary over several roads in the event formats, where the parts are
numbered by the `@index` attribute; in a location set the order of the parts is their order in the itinerary.

[[skupiny]]
==== Non-contiguous location group

A non-contiguous group combines sections that are repeatedly referenced as a whole and do not connect – also
on different roads: an area of regular winter closures, sections around a road weather station. It is a
`predefinedLocationReference` element of type `loc:PredefinedLocationGroup`.

.Group of three non-contiguous sections on two roads
image::skupina-poloh-en.svg[Location group – non-contiguous sections,width=640,align="center"]

* The order of the parts in a group has no meaning.
* A message references the whole group with the type `loc:LocationGroupByReference` (`@targetClass` =
  `loc:PredefinedLocationGroup`).
* Predefined groups are created only for areas that recur; one-off area events are described by the event
  formats with a group of sections directly in the message.

.Location group (sample `predefined_location_loc_group.xml`, shortened)

[[smer]]
=== Direction and bidirectional locations

A location is either one-directional or valid for both directions of travel:

* *FCD sections* are one-directional; each direction is a separate location (`TS02125T15781`,
  `TS15781T02125`).
* *Road weather station sections* and other bidirectional locations are described by *one* location for
  both directions. Each method expresses this in its own way:

[cols="1,4",options="header"]
|===
|Method |Bidirectional location
|ALERT-C |`alertCAffectedDirection` = `both` (one-directional `aligned`)
|OpenLR |`firstDirection` for the location direction and `oppositeDirection` for the opposite direction –
each with its own reference points and offsets; if the opposite direction is not encoded, see <<openlr>>
|Global Network |sections shared by both directions once with `directionRelativeOnLinearSection` = `both`;
if the opposite direction runs elsewhere (separate carriageways, one-way sections), the whole route of the
opposite direction follows the route of the first direction (<<gn>>)
|===

Location groups are not used for bidirectionality. A pair of one-directional locations combined in a group
would require a different reference type (`loc:LocationGroupByReference`), would lose the link between the
directions, and OpenLR and ALERT-C would express bidirectionality twice. Groups are reserved for areas.

[[polohy]]
== Location referencing

A location is linear (`loc:SingleRoadLinearLocation`) – always a contiguous section of one road – and is usually described by several methods depending
on their availability; all describe the same section and at least one must be given. FCD and road weather
station sections are described by at least one method; the location path is given if the location contains GN sections.

A physically point-like place – a road weather station, a bridge, a tunnel entrance – is described as a
short road section on which it lies, in all methods alike: in ALERT-C as a section between two locations,
possibly with identical primary and secondary location; in OpenLR and the GN network as a section of
non-zero length around the place (OpenLR does not allow zero length). Point locations
(`loc:PointLocation`) are not used in the location sets.

[cols="2,3,3",options="header"]
|===
|Method |Element |For whom
|ALERT-C |`alertCLinear` |navigation with the RDS-TMC location table
|OpenLR |`openlrLinear` |matching to any map
|Global Network |`linearWithinLinearElement` (`loc:LinearElementByCode`) |users of the GN network
|Location path |`gmlLineString`, `coordinatesForDisplay` |display on a map without further data (<<prubeh>>)
|Road chainage |`linearWithinLinearElement` with `roadNumber` |not contained in the NDIC sets (optional)
|===
